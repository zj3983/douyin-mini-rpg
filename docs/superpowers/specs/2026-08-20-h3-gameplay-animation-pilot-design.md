# H3 Gameplay Animation Pilot Design

## Goal

Replace the stiff pilot animations for the Qinglan sword cultivator and moss wolf with production-ready motion generated by the existing local MiniMax H3 pipeline on the RTX 5090. Source videos are intermediate assets only. The Cocos runtime continues to consume compact PNG action atlases through the existing animation manifest and `AtlasAnimator` contracts.

## Pilot Scope

The pilot covers one player character and one ground monster:

- Qinglan sword cultivator: idle, sword-flight movement, hand-seal cast, hurt.
- Moss wolf: idle, run, bite-lunge, hurt, death.

The pilot does not regenerate portraits, backgrounds, effects, other monsters, or combat rules. Remaining actors are handled only after the pilot passes visual and runtime acceptance.

## Generation Strategy

Each action is generated as an independent five-second H3 FL2V job. An early Ref2V trial was rejected because it introduced Qinglan identity and gender drift. The accepted pipeline therefore uses the approved character art as an exact first frame, with a matching last frame for looped or boundary-sensitive motion and first-frame conditioning for one-shot actions. Prompts require a locked side-view camera, fixed subject scale, no camera movement, no scene translation, readable limb motion, and an uncluttered removable background.

The character must retain face, hair, costume, weapon, body proportions, and dominant colors. The wolf must retain species silhouette, markings, leg count, tail, and head shape. The action must be physically legible at gameplay scale:

- Sword cultivator idle uses restrained breathing, hair and robe drift, and a stable flying-sword stance.
- Sword-flight movement uses balanced body compensation and cloth drag without running or stepping.
- Hand-seal cast uses visible arm and hand preparation, a held release pose, and recovery without a forward body lunge.
- Wolf run uses a grounded quadruped gait with coherent front and rear leg phases.
- Wolf bite-lunge uses anticipation, launch, bite contact, and recovery without leaving the frame.
- Hurt and death actions have distinct silhouettes and do not resemble locomotion.

Audio generated by H3 is discarded for sprite production.

## Frame Processing

The generated MP4 files remain outside runtime resources. The existing deterministic animation pipeline performs these stages:

1. Decode each video at its native frame rate.
2. Select 6 to 10 useful key frames per ordinary action and up to 12 for attack or death.
3. Remove the flat background and clean alpha edges.
4. Reject blurred, duplicated, malformed, cropped, or identity-drifted frames.
5. Normalize visible scale, ground contact, and action anchor without stretching the subject.
6. Pack one PNG atlas per action and emit the existing animation-manifest data.
7. Generate a contact sheet and metrics report for review.

Video frames are not interpolated around hands, swords, mouths, paws, or contact poses. If H3 produces an invalid phase, that phase is regenerated or omitted rather than repaired through optical interpolation.

## Runtime Integration

The pilot keeps the current atlas-based runtime. No video decoder is added to the game.

- `AtlasAnimator` plays the new atlases at authored frame rates.
- Existing facing logic flips only the visual child and does not alter movement coordinates.
- Event markers trigger sword release and wolf bite contact at authored frames.
- Idle and movement loop; cast, hurt, attack, and death complete once and return through existing state transitions.
- Runtime textures remain lazy-loaded and pooled according to the current actor-atlas system.

## Quality Gates

An action is approved only when all of the following hold:

- The actor identity is consistent across selected frames.
- No body part, sword, ear, tail, paw, or robe edge is unintentionally cropped.
- Ground-contact drift is visually negligible for grounded actions.
- The subject does not resize, stretch, or slide because of frame normalization.
- Player hand-seal and wolf gait are recognizable at actual gameplay scale.
- Attack event markers align with visible contact or release poses.
- Atlas dimensions, frame counts, alpha borders, and manifest paths pass automated validation.
- Replacing the pilot atlases causes no measurable new skill-cast hitch in the existing browser play-agent run.

## Failure Handling

Generation outputs never overwrite approved runtime atlases directly. Every H3 job receives an actor/action identifier and writes to a timestamped source directory. Failed jobs retain their prompt, references, seed, bridge task ID, and error. Processing stops before atlas publication when required actions are missing or validation fails. The previous approved atlas remains available until the complete pilot set passes.

## Verification

Verification includes:

- H3 bridge and remote RTX 5090 readiness checks before submission.
- Contact-sheet review for all nine actions.
- Automated frame, alpha, atlas, and manifest tests.
- Focused Cocos tests for action playback, marker emission, completion, and facing.
- Browser play-agent runs at portrait and landscape sizes, including movement, cast, wolf pursuit, hit, and death.
- Before-and-after screenshots and short action previews stored with the verification report.

## Rollout

The pilot is released behind the existing actor atlas identifiers, so no save migration is required. After approval, the same per-action FL2V process is applied by species and combat role to flying monsters, humanoid enemies, and bosses. Each later batch has its own contact sheet and acceptance record; the pilot does not authorize blind bulk generation.
